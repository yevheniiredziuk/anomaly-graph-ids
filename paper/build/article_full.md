# Анотації
## УКРАЇНСЬКА ВЕРСІЯ

### Назва

**Метод виявлення аномальної мережевої активності на основі графових алгоритмів у Neo4j з використанням Graph Data Science**

### Анотація

**Постановка проблеми.** Сучасні системи виявлення вторгнень (IDS) переважно оперують окремими мережевими потоками (flow-centric парадигма) і побудовані на класифікаторах статистичних ознак. Такий підхід ефективний для сигнатурних атак, але має принципове обмеження — він не враховує структурний контекст взаємодій між хостами, що унеможливлює виявлення атак зі структурним слідом, таких як reconnaissance, бокове переміщення (lateral movement), прихована екфільтрація даних та координована діяльність ботнетів. Графові методи потенційно розв'язують цю проблему, проте їх промислове впровадження стримується складністю інфраструктури та переважним використанням глибоких графових нейронних мереж, що вимагають значних обчислювальних ресурсів і не забезпечують інтерпретовності для операторів SOC.

**Мета роботи** — розробити та експериментально перевірити метод виявлення аномальної мережевої активності на основі класичних графових алгоритмів, реалізований на стеку Neo4j з бібліотекою Graph Data Science (GDS) без залежностей від Python-екосистеми машинного навчання.

**Методологія.** Побудовано формальну модель темпорального мультиграфа мережевого трафіку з типізованими вузлами (хости, сервіси) та ребрами з часовими атрибутами. Запропоновано композитну метрику аномальності вузла, що об'єднує три незалежні графові сигнали: відхилення міри betweenness centrality від baseline-профілю (нормалізоване через сигмоїдальне перетворення), зважену зміну приналежності до спільноти (через intra-community edge ratio як ваговий коефіцієнт), та Jaccard-drift двохкрокової околиці. Метод реалізовано як мультимодульний Java 21 / Spring Boot 3 додаток з інтеграцією Neo4j 2026.03 + GDS 2.x. Для порівняльного експерименту розроблено flow-centric rule-based baseline на PostgreSQL 16 з партиціонованою схемою даних та детекторами типових атак на PL/pgSQL.

**Результати.** Метод перевірено на підмножині публічного датасету CICIDS2017 (понеділок-середа, з очищенням за Engelen та ін.). У прийнятому host-window протоколі оцінювання ($\Delta t = 5$ хв) графовий метод досягає загальних метрик $F_1 = 0{,}013$ ($P = 0{,}007$, $R = 0{,}339$) для fine-grid-best pure-$\alpha_1$ конфігурації та $F_1 = 0{,}011$ для coarse-grid-best композитної конфігурації — проти $F_1 = 0{,}080$ для flow-centric baseline; у прийнятому протоколі graph-метод не перевершує baseline у чутливості виявлення в жодному з протестованих класів атак. Двохрівневий grid search виявив, що композитна метрика не дає стійкої переваги над single-component $\alpha_1$-детектором; $\alpha_2$ (community change) та $\alpha_3$ (Jaccard drift) окремо дають F1 нижче 0,004, і при лінійному об'єднанні з $\alpha_1$ додають шум, а не сигнал. Водночас метод надає інтерпретовані структурні сигнали, недоступні flow-centric підходу, та конкурентну p95-латентність на спеціалізованих графових операціях (approximate betweenness 74,6 мс, Louvain community detection 219,0 мс за 5-хв вікно). Виявлені обмеження артикульовано як мотивацію для напряму attacker/victim channel fusion у подальших роботах.

**Наукова новизна.** Запропоновано інтерпретовану графову альтернативу до GNN-підходів у виявленні мережевих аномалій, реалізовану на промисловому enterprise-стеку без ML-залежностей. Побудовано та експериментально верифіковано композитну метрику аномальності на основі трьох незалежних класичних графових сигналів.

**Практичне значення.** Результати застосовні для побудови систем моніторингу мережевої безпеки в інформаційно-телекомунікаційних мережах військового та державного призначення, а також у навчальному процесі для спеціальностей 122 «Комп'ютерні науки» та 125 «Кібербезпека та захист інформації».

## ENGLISH VERSION

### Title

**A method for network anomaly detection based on graph algorithms in Neo4j using the Graph Data Science library**

### Abstract

**Problem statement.** Modern intrusion detection systems (IDSs) predominantly operate on individual network flows (the flow-centric paradigm) and rely on classifiers over statistical flow features. While effective for signature-based attacks, this paradigm has an intrinsic limitation: it ignores the structural context of inter-host interactions, which precludes detection of attacks with a structural footprint such as reconnaissance, lateral movement, stealthy data exfiltration, and coordinated botnet activity. Graph-based methods potentially address this gap; however, their industrial adoption is hindered by infrastructural complexity and a dominant reliance on deep graph neural networks (GNNs), which demand substantial computational resources and lack the interpretability required for SOC operators.

**Objective.** To develop and experimentally validate a method for network anomaly detection based on classical graph algorithms, implemented on the Neo4j + Graph Data Science (GDS) stack without dependencies on the Python machine-learning ecosystem.

**Methodology.** A formal model is introduced describing network traffic as a temporal multigraph with typed nodes (hosts, services) and edges carrying temporal attributes. A composite node-level anomaly metric is proposed that combines three independent graph signals: (1) the deviation of betweenness centrality from a baseline profile, normalised via sigmoidal transformation; (2) the weighted change of community membership, using an intra-community edge ratio as a confidence weight; and (3) the Jaccard drift of a node's 2-hop neighborhood. The method is implemented as a multi-module Java 21 / Spring Boot 3 application integrated with Neo4j 2026.03 and GDS 2.x. For comparative evaluation, a flow-centric rule-based baseline is implemented in PostgreSQL 16, featuring a partitioned schema and PL/pgSQL detectors for canonical attack types.

**Results.** The method is evaluated on a subset of the public CICIDS2017 dataset (Monday-Wednesday, cleaned according to Engelen et al.). Under the adopted host-window evaluation protocol ($\Delta t = 5$ min), the graph-based method attains overall $F_1 = 0.013$ ($P = 0.007$, $R = 0.339$) for the fine-grid-best pure-$\alpha_1$ configuration and $F_1 = 0.011$ for the coarse-grid-best composite configuration, against $F_1 = 0.080$ for the flow-centric baseline; it does not exceed the baseline in detection recall on any tested attack class under this protocol. A two-level grid search (coarse simplex × fine corners) shows that the linear composite metric provides no stable advantage over a single-component $\alpha_1$ detector; $\alpha_2$ (community change) and $\alpha_3$ (2-hop Jaccard drift) individually yield $F_1 < 0.004$ and, when linearly combined with $\alpha_1$, add noise rather than signal. The method nevertheless delivers interpretable structural signals unavailable to the flow-centric approach and competitive p95 latency on graph-specific operations (approximate betweenness 74.6 ms, Louvain community detection 219.0 ms per 5-min window). The identified limitations are articulated as motivation for an attacker/victim channel fusion direction in future work.

**Scientific contribution.** An interpretable graph-based alternative to GNN approaches in network anomaly detection is proposed, implemented on an industrial enterprise stack without ML dependencies. A composite anomaly metric combining three independent classical graph signals is introduced and experimentally verified.

**Practical significance.** The results apply to the construction of network security monitoring systems in information-communication networks for military and governmental applications, as well as in the educational process for specialties 122 "Computer Science" and 125 "Cybersecurity and Information Protection".

### Keywords

intrusion detection; graph database; Neo4j; Graph Data Science; composite anomaly metric; betweenness centrality; community detection; CICIDS2017

## 1. ВСТУП

### 1.1. Постановка проблеми

Сучасні інформаційно-телекомунікаційні мережі — корпоративні, індустріальні, мережі спеціального призначення — оперують обсягами мережевого трафіку, які роблять ручний моніторинг неможливим. Системи виявлення вторгнень (Intrusion Detection Systems, IDS) стають обов'язковою складовою оборонного контуру, причому клас задач, який вони розв'язують, принципово змінився: разом із сигнатурними атаками (відомі експлойти, volumetric DDoS) IDS мають виявляти поведінкові відхилення, характерні для цілеспрямованих атак (Advanced Persistent Threats, APT), прихованих сканувань, lateral movement у скомпрометованих сегментах та екфільтрації даних у режимі «low-and-slow» [3, 6, 9].

Переважна більшість існуючих IDS-рішень — як комерційних, так і академічних — побудована на **flow-centric парадигмі**: одиницею аналізу є окремий мережевий потік (network flow), описаний вектором статистичних ознак (тривалість, кількість переданих байт і пакетів, розподіл довжин пакетів, частота прапорців TCP тощо). Над цим вектором працює класифікатор — від сигнатурних правил у системах типу Snort/Suricata до глибоких нейронних мереж [4, 20]. Такий підхід ефективний для виявлення атак з чіткими сигнатурами окремого потоку, однак має три принципові обмеження, які стали очевидними в останньому десятилітті.

**По-перше, ігнорування контексту взаємодій.** Коли хост *A* одного дня вперше звертається до десятків нових хостів у внутрішній мережі — це класичний патерн reconnaissance або бокового переміщення скомпрометованого зловмисника; але кожен окремий потік, ініційований *A*, з точки зору flow-centric детектора є абсолютно нормальним. Структурна аномалія не є властивістю жодного окремого потоку — вона є властивістю **сукупності потоків** і тих зв'язків, які ці потоки утворюють між хостами [6, 9].

**По-друге, слабке виявлення повільних атак.** Техніки низькоінтенсивного сканування портів, підбору паролів з великими затримками, прихованої екфільтрації з дозованою швидкістю свідомо спроєктовані так, щоб залишитись під порогами flow-based детекторів. Це одна з основних причин, чому APT-активність часто виявляється постфактум після багатомісячної присутності в мережі [3].

**По-третє, нездатність виявляти раптову зміну ролі хоста.** Звичайна workstation, що починає поводитися як мережевий хаб (велика кількість з'єднань у коротких часових проміжках з високою центральністю в графі комунікацій), з великою ймовірністю є скомпрометованим пристроєм, що використовується як pivot-вузол у внутрішньомережевій атаці. Ця поведінкова зміна є **структурною** — вона виражається через топологічні та часові характеристики графа взаємодій, а не через статистику окремих потоків [6, 8].

Зазначені обмеження природно розв'язуються шляхом переходу від flow-centric до **graph-based парадигми**: мережевий трафік представляється як темпоральний граф (хости — вузли, комунікації — ребра з часовими атрибутами), а виявлення аномалій зводиться до застосування графових алгоритмів — мір центральності (centrality), детекції спільнот (community detection), аналізу подібності околиць вузлів — до цього графа [1, 2, 5]. Експериментальні роботи останніх років переконливо демонструють, що graph-based IDS виявляють структурні атаки (lateral movement, infiltration, botnet C&C) з чутливістю, недосяжною для flow-centric підходів [6, 7]. Водночас промислове впровадження таких рішень стримується двома чинниками: складністю інфраструктури (більшість академічних прототипів побудовані на Python + спеціалізовані графові бібліотеки для ML і не інтегруються з enterprise Java-середовищами) та переважаючим використанням глибоких графових нейронних мереж (Graph Neural Networks, GNN), які потребують значних обчислювальних ресурсів для навчання та інтерпретації [9, 10].

**Таким чином, актуальною є задача розробки методу виявлення мережевих аномалій на основі графових алгоритмів, який (а) не вимагає навчання глибоких моделей, (б) реалізується на стандартному enterprise-стеку (Java + промислова графова СУБД), (в) забезпечує інтерпретовність результатів та (г) надає експериментально підтверджену перевагу над flow-centric baseline при розумних обчислювальних витратах.**

### 1.2. Актуальність дослідження

Актуальність задачі підсилюється трьома чинниками, специфічними для сучасного українського контексту.

По-перше, ескалація кіберзагроз у період збройного протистояння вимагає рішень, що виявляють раніше невідомі (zero-day) атаки через поведінкові аномалії, а не через сигнатури [23].

По-друге, зростання вимог до **інтерпретовності** IDS-рішень — ані voluntarily, ані в рамках майбутнього регулювання штучного інтелекту (наприклад, EU AI Act, на який орієнтується й українське законодавство) — робить «чорноскринькові» deep-learning моделі менш прийнятними для security-критичних застосувань [22].

По-третє, дефіцит кваліфікованих SOC-аналітиків у військових та державних організаціях робить принципово важливим такі методи виявлення, результати яких можуть бути інтерпретовані оператором без глибоких знань машинного навчання — що є природною властивістю графових методів, де кожна аномальна ознака вузла (відхилення центральності, зміна community membership, трансформація околиці) має прозоре топологічне значення [9, 23].

### 1.3. Практичне значення роботи

Результати дослідження можуть бути застосовані для побудови систем моніторингу мережевої безпеки в інформаційно-телекомунікаційних мережах військового та державного призначення, де ключовими критеріями є інтерпретовність сигналів для операторів SOC, відсутність залежностей від закритих закордонних ML-платформ та можливість локального розгортання на стандартному enterprise-стеку. Матеріали роботи також можуть бути використані в освітньому процесі при підготовці фахівців за спеціальностями 122 «Комп'ютерні науки» та 125 «Кібербезпека та захист інформації» в рамках навчальних дисциплін, пов'язаних з графовим моделюванням даних та аналізом мережевої безпеки.

### 1.4. Аналіз останніх досліджень і публікацій (стислий)

Задача виявлення мережевих аномалій на основі графових методів активно розвивається з середини 2010-х років. Фундаментальні засади сформульовано в роботах Akoglu, Tong та Koutra [2], де запропоновано таксономію graph-based anomaly detection методів. Серед сучасних підходів домінують дві лінії: (а) методи, побудовані на класичних графових алгоритмах — мірах центральності, детекції спільнот, сигнатурах підграфів [1, 6, 7], та (б) нейромережеві підходи на основі Graph Neural Networks, зокрема temporal GNN з послідовнісними кодерами [6, 10]. Детальний огляд цих напрямів, а також положення запропонованої роботи серед них, наведено в розділі 2.

### 1.5. Не вирішена раніше частина проблеми

Аналіз літератури показує, що, попри значну кількість робіт з графового виявлення аномалій у мережах, залишається відкритим питання **інженерної інтеграції** таких методів у enterprise-стек на основі промислової графової СУБД (Neo4j) з мінімізацією залежностей від спеціалізованих Python-бібліотек машинного навчання. Переважна більшість опублікованих рішень вимагає окремого ML-конвеєра на Python з подальшою інтеграцією результатів у основну систему, що створює операційні ризики (дублювання стеку, складність розгортання, проблеми підтримки) у військових та державних організаціях із жорсткими вимогами до простоти та керованості інфраструктури.

Окреме питання, недостатньо висвітлене в наявних роботах, — експериментальне порівняння продуктивності графової та реляційної парадигми саме на задачах виявлення мережевих аномалій. Загальні бенчмарки Neo4j проти реляційних СКБД відомі [15], однак їх результати отримано на безпековій задачі, а не на синтетичних або соціальних графах. Перенесення цих результатів на контекст IDS потребує окремої експериментальної перевірки.

### 1.6. Мета і завдання дослідження

**Мета роботи** — розробити та експериментально перевірити метод виявлення аномальної мережевої активності на основі графових алгоритмів, реалізований на стеку Neo4j + Graph Data Science без ML-залежностей, з експериментальним порівнянням ефективності та продуктивності з flow-centric rule-based baseline на публічному датасеті CICIDS2017.

Для досягнення мети поставлено такі **завдання**:

1. Виконати аналіз сучасних підходів до виявлення мережевих аномалій у flow-centric та graph-based парадигмах; визначити переваги та обмеження кожного підходу.
2. Побудувати формальну модель темпорального мультиграфа мережевого трафіку, придатну для зберігання в графовій СУБД Neo4j.
3. Розробити композитну метрику аномальності вузла, що поєднує три незалежні графові сигнали: відхилення міри центральності, зміну приналежності до спільноти та трансформацію околиці в часових вікнах.
4. Реалізувати метод у вигляді пайплайну на основі Neo4j Graph Data Science та інтеграційного шару Spring Data Neo4j, без Python-залежностей.
5. Реалізувати flow-centric rule-based baseline на PostgreSQL з PL/pgSQL.
6. Провести експериментальну перевірку методу на датасеті CICIDS2017 за метриками Precision, Recall, F1 (для якості виявлення) та query latency, throughput (для продуктивності).
7. Сформулювати обмеження методу та напрями подальших досліджень.

### 1.7. Структура статті

Решта статті організована так. У розділі 2 наведено аналіз останніх досліджень і публікацій у сферах графових методів виявлення аномалій, нейромережевих IDS та продуктивності графових СКБД. Розділ 3 містить формальну модель темпорального мультиграфа мережевого трафіку, визначення композитної метрики аномальності та відповідну Neo4j-схему. Розділ 4 описує метод виявлення аномалій — структуру пайплайну, побудову baseline-профілю, алгоритм sliding window detection. Розділ 5 присвячений реалізації: архітектурі системи, ключовим Cypher-запитам та інтеграції з Neo4j GDS через Java-драйвер. У розділі 6 наведено результати експериментальної оцінки на датасеті CICIDS2017 у порівнянні з PostgreSQL-based baseline, включно з аналізом чутливості до параметрів та обговоренням обмежень. Розділ 7 містить висновки та напрями подальших досліджень.

## 2. АНАЛІЗ ОСТАННІХ ДОСЛІДЖЕНЬ І ПУБЛІКАЦІЙ

Для систематизації аналізу розглянемо предметну область у чотирьох вимірах: (1) еволюція підходів до виявлення мережевих аномалій — від flow-centric до graph-based парадигми; (2) сучасні методи graph-based IDS з окремим розглядом класичних графових алгоритмів та нейромережевих підходів; (3) Neo4j та бібліотека Graph Data Science як платформа промислової реалізації; (4) локальні українські дослідження в цій сфері та їх позиціонування.

### 2.1. Від flow-centric до graph-based виявлення аномалій

Історично задача виявлення мережевих вторгнень формулювалася як задача класифікації окремих потоків (flows) або пакетів. У фундаментальному огляді Khraisat та ін. [4] систематизовано два класи IDS: сигнатурні (signature-based) та аномалійні (anomaly-based). Перший клас базується на точному співставленні з базою відомих патернів атак — його основна проблема полягає у нездатності виявляти нові (zero-day) загрози. Другий клас будує поведінкову модель «нормального» трафіку і сигналізує про відхилення — його основна проблема полягає у високій частоті хибно-позитивних спрацювань (false positives), що викликає явище «alert fatigue» у операторів SOC.

Спроби вирішити проблему хибно-позитивних спрацювань призвели до активного використання методів машинного та глибокого навчання. Огляд Aldweesh та ін. [20] систематизує deep-learning підходи до IDS, виділяючи автокодери, LSTM-мережі, CNN та їх гібриди. Суттєвою особливістю цих методів є те, що вони залишаються в межах flow-centric парадигми: одиницею аналізу залишається окремий потік, а нейромережа лише замінює «ручне» конструювання ознак навчанням їх із даних.

Паралельно в академічному середовищі формується усвідомлення, що flow-centric парадигма має фундаментальне обмеження — вона ігнорує **структуру взаємодій** між хостами. У піонерській роботі Akoglu та ін. [2] сформульовано таксономію методів виявлення аномалій у графах, а в огляді Ma та ін. [1] систематизовано вже подальший етап — глибоке навчання на графах для anomaly detection. Ключова теза цієї лінії досліджень: багато атак залишають сліди саме на рівні зв'язків між хостами (або між хостом і сервісом, процесом і файлом, користувачем і ресурсом), а не на рівні окремих комунікаційних подій. Класичні приклади — lateral movement у скомпрометованій мережі, координовані DDoS-атаки з використанням ботнетів, непрямі шляхи екфільтрації даних через проміжні хости.

Таким чином, у сучасній літературі закріпилося розуміння, що graph-based IDS не є конкурентом flow-centric підходам, а є **доповненням**, яке ефективніше саме для виявлення **структурних аномалій**. Це формує актуальний методологічний контекст: питання не в тому, «чи потрібні графові методи», а в тому, «як їх оптимально поєднати з існуючими flow-based детекторами». Запропонована в цій роботі модель розглядає graph-based підхід саме як окремий канал виявлення, що доповнює класичні flow-based детектори.

### 2.2. Графові методи виявлення аномалій у мережах

Графові методи виявлення мережевих аномалій можна розділити на дві великі групи: підходи на основі класичних графових алгоритмів (міри центральності, детекція спільнот, сигнатури підграфів) та підходи на основі графових нейронних мереж (GNN).

**Класичні графові методи** використовують формалізм теорії графів напряму. Roshandel [7] у систематичному порівняльному аналізі показує, що графовий детектор аномалій, побудований на класичних мірах центральності та модульності, на датасеті CICIDS2017 демонструє конкурентоспроможну точність порівняно з комерційною системою Zeek. Це важливий результат, який демонструє, що класичні графові алгоритми не є «теоретичною цікавинкою», а мають практичне значення, не поступаючись промисловим рішенням.

Принциповою перевагою класичних підходів є **інтерпретовність**. Коли система сигналізує про аномальність хоста, оператор може швидко зрозуміти причину: хост раптово став мати високу betweenness centrality (виступає посередником для невідповідної кількості з'єднань між іншими хостами); хост перейшов в іншу спільноту (змінив свою поведінкову роль); околиця хоста різко змінилася (хост почав комунікувати з нетиповими для нього вузлами). Кожна з цих метрик має безпосередню топологічну інтерпретацію, яку можна пояснити в доповіді про інцидент. Це контрастує з GNN-підходами, де «підозрілість» хоста є скаляром на виході нейромережі без прозорого пояснення.

**Методи на основі графових нейронних мереж** представлені в низці свіжих робіт. Узагальнюючі огляди Bilot та ін. [3] та Computers & Security [9] систематизують цей напрямок: типова архітектура — це комбінація GNN-енкодера (GCN, GraphSAGE, GAT) з послідовнісним декодером (LSTM, Transformer) для врахування часової динаміки графа. Перевага — висока точність у задачах link prediction та node classification. Недоліки — (а) необхідність значних обсягів мічених даних для навчання, (б) високі обчислювальні витрати як на тренування, так і на інференс, (в) низька інтерпретовність рішень.

Особливо показовою є робота King та Huang «Euler» [6], що стала ключовим орієнтиром у сучасній літературі з виявлення lateral movement. Автори формалізують задачу детекції бокового переміщення як задачу temporal link prediction: мережеві з'єднання представляються як часово-мічений граф, GNN навчається на «нормальних» з'єднаннях передбачувати появу ребер, а аномальні ребра (ті, яким модель присвоює низьку ймовірність) інтерпретуються як потенційні сліди атаки. Euler демонструє перевагу над класичними baseline'ами, але водночас вимагає значних обчислювальних ресурсів — автори експериментують на enterprise-масштабних датасетах з мільярдами подій, недосяжних у типовому академічному середовищі.

Ця обставина актуалізує питання **ресурсно-економних альтернатив**: чи можна досягти прийнятної якості виявлення структурних аномалій без необхідності навчати глибокі моделі? Роботи Altaf та ін. [8] та огляд Electronics [10] свідчать, що для певних класів атак (коли структурний слід атаки виражений у явному вигляді — як при port scan, infiltration, C&C-комунікаціях ботнету) класичні графові алгоритми можуть забезпечувати порівнянну або близьку якість при суттєво нижчих обчислювальних витратах.

Запропонований у цій роботі підхід позиціонується саме у цій ніші: **класичні графові алгоритми (betweenness centrality, Louvain community detection, Jaccard similarity на k-hop околицях), об'єднані композитною метрикою, як легка інтерпретована альтернатива до GNN-підходів для задач виявлення структурних аномалій**.

### 2.3. Проблема інженерної реалізації та Neo4j як платформа

Незалежно від вибору між класичними та нейромережевими графовими методами, в академічних роботах залишається недостатньо висвітленим питання **інженерної реалізації** графових IDS у промислових умовах.

Переважна більшість опублікованих прототипів побудована на Python-стеку з бібліотеками NetworkX, PyTorch Geometric, DGL. Ці інструменти чудово підходять для дослідницької роботи, але створюють три проблеми для промислового впровадження. По-перше, вимагають окремого ML-конвеєра, який треба інтегрувати з основною системою моніторингу мережевої безпеки (зазвичай побудованою на Java / .NET / C++). По-друге, NetworkX зберігає граф у пам'яті процесу — що робить масштабування нетривіальним. По-третє, більшість Python-бібліотек орієнтована на batch-обробку, а не на incremental updates, які потрібні для real-time IDS.

Альтернативою є побудова архітектури навколо **промислової графової бази даних** — це вирішує проблеми зберігання та incremental updates (граф персистентний, оновлюється транзакційно), а також забезпечує природну інтеграцію з enterprise-середовищами через стандартні драйвери.

Серед наявних графових СКБД Neo4j посідає провідну позицію: за даними індексу DB-Engines, Neo4j стабільно зберігає перше місце серед графових СКБД протягом понад десяти років [15]. Принципово важливою обставиною для задачі цієї роботи є наявність **Neo4j Graph Data Science (GDS)** — бібліотеки графових алгоритмів, що нативно інтегрована з Neo4j і викликається з мови запитів Cypher [14]. GDS містить реалізації всіх класичних алгоритмів, потрібних у цій роботі: betweenness centrality (точна та наближена sampling-based версія за Brandes [13]), Louvain community detection [12], k-hop neighborhood операції, Node Similarity (Jaccard, косинусна). Важливо, що GDS реалізована на JVM, що дозволяє викликати її з Java-додатків без додаткових мовних мостів.

Порівняльні бенчмарки Neo4j та реляційних СКБД представлені в кількох роботах. Найпоказовіший — Messina та ін. [15]: у peer-reviewed дослідженні в Applied Sciences продемонстровано, що на запитах типу «друзі друзів» (класичний multi-hop traversal, структурно еквівалентний нашій задачі аналізу околиці хоста) Neo4j зберігає практично константну продуктивність, тоді як MySQL з JPA повільнішає в 5–9 разів зі зростанням глибини запиту. Споріднене дослідження Rodrigue та Jain [16] повідомляє про середнє прискорення у 193 рази для рекурсивних запитів у Neo4j порівняно з MySQL. Ці результати підтверджують теоретичні очікування: при join-heavy навантаженні реляційні СКБД виконують логарифмічно складні операції, тоді як графові СКБД, де зв'язки зберігаються як фізичні вказівники, виконують константний перехід. Однак важливим застереженням є те, що згадані бенчмарки проведені на синтетичних або соціальних графах, а не на графах мережевого трафіку — перенесення результатів на IDS-контекст потребує експериментальної верифікації, яка і є однією з задач цієї роботи.

Треба також зазначити, що всі наведені бенчмарки стосуються **читання** — для сценарію великого initial load даних (наприклад, завантаження CICIDS2017) реляційні СКБД традиційно демонструють кращу throughput. Це означає, що порівняння Neo4j vs PostgreSQL має бути проведене саме за робочими сценаріями IDS (incremental insert + multi-hop query), а не за абстрактним «loading performance».

### 2.4. Локальні дослідження та військовий контекст

Українська наукова дискусія у сфері IDS та графових методів активно розвивається. У роботі Ільїна та Старинського [23], опублікованій у спеціалізованому військово-орієнтованому виданні «Сучасні інформаційні технології у сфері безпеки та оборони», запропоновано математичну модель виявлення вторгнень з використанням нейронної мережі на основі автоенкодерів для захисту інформаційно-телекомунікаційних мереж військового призначення. Робота чітко позиціонує проблему високого обсягу мережевих даних та необхідності автоматизованого поведінкового аналізу, однак залишається в межах flow-centric парадигми — одиницею аналізу є окремий трафіковий запис, а графова структура взаємодій між хостами не використовується.

Ільєнко та ін. [22] в роботі, опублікованій у цільовому журналі «Кібербезпека: освіта, наука, техніка», систематизують перспективи інтеграції штучного інтелекту в системи кібербезпеки, зокрема в контекст виявлення загроз. Робота має оглядовий характер і закладає контекстуальний фундамент для впровадження інтелектуальних методів, зокрема визначаючи як один з ключових напрямків — автоматичне виявлення аномалій. Подальше розширення цього напрямку представлене в роботі Ільєнко та ін. [24], де наведено аналіз потенціалу та викликів застосування штучного інтелекту у кібербезпеці. Водночас конкретні графові моделі (включно з Neo4j-реалізацією) в цих роботах не розглядаються.

Таким чином, українська наукова дискусія демонструє: (а) наявність активного інтересу до інтелектуальних методів виявлення кіберзагроз, (б) чітке усвідомлення специфіки військових інформаційно-телекомунікаційних мереж, (в) переважну орієнтацію на нейромережеві (deep-learning) методи. Графові методи на основі промислових графових СКБД — напрямок, що залишається недостатньо представленим у локальній літературі, що додатково підтверджує актуальність запропонованої роботи.

### 2.5. Виділення не вирішеної раніше частини проблеми

Проведений аналіз літератури дозволяє сформулювати конкретні прогалини, які ця робота заповнює.

**По-перше,** в сучасній літературі переважає дихотомія «flow-centric rule-based baselines vs graph-based deep learning», без достатньої представленості **проміжної ніші** — графових методів на основі класичних алгоритмів, реалізованих на промисловій графовій СКБД з інженерно реалістичною інтеграцією в enterprise-середовище.

**По-друге,** бенчмарки Neo4j проти реляційних СКБД, попри свою чисельність, проводилися на загальних або синтетичних датасетах. Порівняльна продуктивність графової та реляційної парадигм саме на задачах виявлення мережевих аномалій на реалістичному IDS-датасеті не досліджена.

**По-третє,** українська наукова дискусія у сфері IDS для військових інформаційно-телекомунікаційних мереж орієнтована переважно на deep-learning методи, що створює проблему інтерпретовності та ресурсних вимог. Інтерпретовані графові альтернативи залишаються за межами активного обговорення.

**По-четверте,** композитні метрики аномальності, що об'єднують кілька незалежних графових сигналів (центральність, community membership, зміна околиці) з дослідженим впливом ваг компонентів, висвітлені в літературі переважно на теоретичному рівні, без експериментальної валідації на мережевих датасетах.

Саме заповнення цих чотирьох прогалин — на методологічному, експериментальному, локально-контекстуальному та метричному рівнях — визначає науковий внесок запропонованої роботи, формально представлений у розділі 3.

## 3. ФОРМАЛЬНА МОДЕЛЬ

Цей розділ містить формальне визначення моделі, на якій базується запропонований метод. Виклад структуровано так: спершу вводимо модель темпорального мультиграфа мережевого трафіку (3.1), далі — операції темпоральних вікон для сегментації неперервного потоку подій у дискретні знімки графа (3.2), потім визначаємо три компоненти композитної метрики аномальності (3.3), об'єднуємо їх у підсумкову метрику з правилом прийняття рішення (3.4), та завершуємо розділ описом реалізації моделі у вигляді Neo4j-схеми (3.5).

### 3.1. Темпоральний мультиграф мережевого трафіку

Нехай мережевий трафік в інфокомунікаційній системі описується темпоральним мультиграфом виду:

$$G = (V,\,E,\,T,\,\phi_V,\,\phi_E,\,\tau,\,\alpha) \tag{3.1}$$

де:
- $V$ — скінченна множина вузлів, кожен з яких представляє мережевий хост або сервіс;
- $E \subseteq V \times V \times T \times \mathbb{N}$ — множина спрямованих темпоральних ребер; четвертий компонент — порядковий номер ребра для розрізнення паралельних ребер (що робить $G$ мультиграфом);
- $T \subseteq \mathbb{R}_{\geq 0}$ — неперервна часова вісь;
- $\phi_V: V \to L_V$ — функція типізації вузлів, $L_V = \{\mathrm{Host},\,\mathrm{Service}\}$;
- $\phi_E: E \to L_E$ — функція типізації ребер, $L_E = \{\mathrm{CONNECTS\_TO},\,\mathrm{HOSTS}\}$;
- $\tau: E \to T \times T$ — функція часових інтервалів ребра, $\tau(e) = (t_\mathrm{start}(e),\,t_\mathrm{end}(e))$;
- $\alpha: E \to \mathcal{A}$ — функція атрибутів ребра, $\mathcal{A}$ — простір векторів атрибутів.

Для ребер типу CONNECTS_TO вектор атрибутів має форму:

$$\alpha(e) = \langle \mathrm{proto},\,\mathrm{src\_port},\,\mathrm{dst\_port},\,\mathrm{bytes\_fwd},\,\mathrm{bytes\_bwd},\,\mathrm{pkts\_fwd},\,\mathrm{pkts\_bwd},\,\mathrm{flags} \rangle \tag{3.2}$$

де `proto` — мережевий протокол (TCP/UDP/ICMP), `src_port`/`dst_port` — номери портів, пари `bytes_*/pkts_*` — обсяги трафіку у forward- і backward-напрямках відносно ініціатора з'єднання, `flags` — побітове об'єднання прапорців TCP, присутніх у потоці. Ребра типу HOSTS моделюють відношення «хост надає сервіс» і мають обмежену множину атрибутів (лише тип сервісу).

Зауваження щодо вибору моделі. Фундаментальна теза, на якій будується запропонований метод, полягає в тому, що мережевий трафік є **інтринсично темпоральним** феноменом, і представлення його у формі статичного агрегованого графа призводить до втрати інформації, критичної для виявлення поведінкових аномалій. Формалізм (3.1) зберігає темпоральну структуру, допускаючи наявність паралельних ребер з різними часовими інтервалами, що природно для моделювання множинних послідовних з'єднань між одними й тими самими парами хостів.

### 3.2. Темпоральні вікна

Задача виявлення аномалій в неперервному потоці мережевих подій вимагає дискретизації часової осі у вікна фіксованої тривалості. Нехай задано параметр тривалості аналітичного вікна $\Delta t > 0$. Тоді для будь-якого моменту часу $t \in T$ визначається множина ребер, що потрапляють у вікно з центром у $t$:

$$W(t,\,\Delta t) = \{e \in E : t_\mathrm{start}(e) \in [t - \Delta t,\,t)\} \tag{3.3}$$

На основі $W(t,\,\Delta t)$ будується індукований підграф $G_t$, що представляє стан мережі у момент $t$:

$$G_t = (V_t,\,W(t,\,\Delta t),\,\phi_V|_{V_t},\,\phi_E|_{W(t,\,\Delta t)},\,\tau|_{W(t,\,\Delta t)},\,\alpha|_{W(t,\,\Delta t)}) \tag{3.4}$$

де $V_t = \{v \in V : \exists\,e \in W(t,\,\Delta t),\ v \in \mathrm{endpoints}(e)\}$ — множина вузлів, задіяних у комунікаціях поточного вікна.

Для побудови референсного профілю «нормальної» поведінки вводимо також **baseline-вікно** тривалості $\Delta t_b \gg \Delta t$. Типові пропорції: $\Delta t = 5$–10 хв для аналітичного вікна, $\Delta t_b = 6$–24 год для baseline. Baseline-вікно будується на попередньо верифікованих «чистих» проміжках роботи мережі (без зафіксованих інцидентів) і використовується для обчислення статистик, відносно яких оцінюються відхилення на поточних вікнах.

Крок просування аналітичного вікна $\delta t \leq \Delta t$ визначає roll-over частоту: при $\delta t = \Delta t$ вікна не перекриваються, при $\delta t < \Delta t$ — послідовні вікна мають перетин, що забезпечує згладжування рішення за рахунок обчислювальних витрат. У подальшому експерименті (розділ 6) оптимальні значення $\Delta t$ та $\delta t$ визначаються емпірично.

### 3.3. Компоненти композитної метрики аномальності

Для кожного хоста $v \in V$ на кожному вікні $t$ обчислюється три незалежні показники, що характеризують різні аспекти потенційної аномальності поведінки.

#### 3.3.1. Компонент $\alpha_1$: відхилення центральності

Першим компонентом є нормалізоване відхилення центральності вузла у поточному вікні від його статистичного baseline-значення. Як міра центральності використовується **betweenness centrality**, яка для вузла $v$ у графі $G_t$ визначається згідно з [13] як:

$$BC_t(v) = \sum_{s \neq v \neq u,\ s,u \in V_t} \frac{\sigma_{su}^{G_t}(v)}{\sigma_{su}^{G_t}} \tag{3.5}$$

де $\sigma_{su}^{G_t}$ — кількість найкоротших шляхів між вершинами $s$ та $u$ у графі $G_t$, а $\sigma_{su}^{G_t}(v)$ — кількість таких шляхів, що проходять через $v$.

Вибір betweenness centrality обґрунтовано семантично: ця міра ефективно виявляє «bridge»-вузли у графі, що є природним сигналом для компрометованих хостів, які використовуються як pivot-вузли у lateral movement [6].

На основі baseline-вікна обчислюються статистики вузла $v$:

$$\mu^{BC}_v = \mathbb{E}_{t' \in \mathrm{baseline}}[BC_{t'}(v)], \quad \sigma^{BC}_v = \sqrt{\mathrm{Var}_{t' \in \mathrm{baseline}}[BC_{t'}(v)]} \tag{3.6}$$

Компонент $\alpha_1$ визначається як z-score відхилення поточного значення від baseline:

$$\alpha_1(v,\,t) = \frac{|BC_t(v) - \mu^{BC}_v|}{\sigma^{BC}_v + \varepsilon} \tag{3.7}$$

де $\varepsilon > 0$ — регуляризаційна константа, що запобігає діленню на нуль для вузлів зі сталою центральністю у baseline (наприклад, типові endpoint-workstations). У подальшому експерименті встановлюється $\varepsilon = 10^{-6}$, що є на порядки меншим за типові значення $\sigma^{BC}_v$ і не спотворює результат для вузлів з ненульовою дисперсією.

Інтерпретація: $\alpha_1(v,\,t) \geq 3$ відповідає статистично значущому відхиленню (правило «трьох сігм»), проте в рамках композитної метрики пороги визначаються не покомпонентно, а на сукупному показнику (див. 3.4).

#### 3.3.2. Компонент $\alpha_2$: зміна приналежності до спільноти

Другим компонентом є показник зміни структурної спільноти вузла між послідовними вікнами. Нехай $C: V_t \to \mathbb{N}$ — функція приналежності вузла до спільноти, отримана шляхом застосування алгоритму Louvain [12] до графа $G_t$. Louvain обрано через (а) $O(|V|\log|V|)$-подібну асимптотичну складність у практичних графах, придатну для інкрементального обчислення, (б) природну інтерпретацію через оптимізацію модульності.

Поточна та попередня спільноти вузла позначаються $C_t(v)$ та $C_{t-\delta t}(v)$ відповідно. Зміна приналежності реєструється як бінарна подія, зваженої на силу приналежності до попередньої спільноти:

$$\alpha_2(v,\,t) = \mathbb{1}[C_t(v) \neq C_{t-\delta t}(v)] \cdot \rho(v,\,t - \delta t) \tag{3.8}$$

де $\mathbb{1}[\cdot]$ — індикаторна функція, а $\rho(v,\,t - \delta t) \in [0,\,1]$ — **сила приналежності** вузла до своєї попередньої спільноти, визначена як частка ребер вузла, що ведуть у його спільноту (intra-community edge ratio):

$$\rho(v,\,t') = \frac{|\{e \in E_{t'}(v) : \mathrm{community}(\mathrm{other}(e,v)) = C_{t'}(v)\}|}{|E_{t'}(v)|} \tag{3.9}$$

Тут $E_{t'}(v) \subseteq W(t',\,\Delta t)$ — множина ребер вузла $v$ у вікні $t'$, $\mathrm{other}(e,\,v)$ — протилежний кінець ребра $e$ відносно $v$, а $C_{t'}(v)$ — ідентифікатор спільноти вузла $v$ у вікні $t'$. У крайньому випадку $|E_{t'}(v)| = 0$ (вузол ізольований) приймаємо $\rho(v,\,t') = 0$.

Семантичне обґрунтування: $\rho(v, t') = 1$ означає, що всі комунікаційні контакти вузла зосереджені в межах його спільноти — вузол є «ядерним» для свого кластеру. $\rho(v, t') = 0$ означає, що жоден з контактів вузла не належить до формально визначеної для нього спільноти, що типово для периферійних «мостових» вузлів між кластерами.

Зважування через $\rho$ є принципово важливим: зміна приналежності периферійного вузла (з $\rho \approx 0$) має незначну діагностичну вагу — такі переходи є природним шумом у кластеризації, зумовленим невизначеністю приналежності слабко пов'язаних вузлів. Натомість зміна приналежності центрального для своєї спільноти вузла (з $\rho$ близьким до 1) є сильним сигналом структурної трансформації поведінки.

Обчислювально формула (3.9) реалізується за один прохід по ребрах вузла, що дає складність $\mathcal{O}(d_v)$ на вузол, де $d_v$ — ступінь вузла. Це суттєво економніше порівняно з альтернативою через повторне обчислення модульності.

#### 3.3.3. Компонент $\alpha_3$: зміна околиці

Третій компонент реєструє трансформацію безпосередньої околиці вузла. Нехай $N_k^t(v) \subseteq V_t$ — множина вузлів у $k$-транзитивній околиці вузла $v$ у графі $G_t$:

$$N_k^t(v) = \{u \in V_t : \mathrm{dist}_{G_t}(v,\,u) \leq k\} \setminus \{v\} \tag{3.10}$$

де $\mathrm{dist}_{G_t}$ — відстань (кількість ребер) у графі $G_t$. У рамках цієї роботи приймається $k = 2$: сусіди першого порядку фіксують прямі комунікаційні контакти, сусіди другого — потенційні проміжні точки lateral movement.

Ступінь трансформації околиці вимірюється як Jaccard drift:

$$\alpha_3(v,\,t) = 1 - J\bigl(N_k^t(v),\,N_k^{t - \delta t}(v)\bigr) = 1 - \frac{|N_k^t(v) \cap N_k^{t - \delta t}(v)|}{|N_k^t(v) \cup N_k^{t - \delta t}(v)|} \tag{3.11}$$

$\alpha_3(v,\,t) = 0$ означає ідентичні околиці, $\alpha_3(v,\,t) = 1$ — повну заміну околиці (жодного спільного сусіда з попереднім вікном). Випадок, коли $|N_k^t(v) \cup N_k^{t - \delta t}(v)| = 0$, трактується як $\alpha_3(v,\,t) = 0$ (вузол не виявляв активності у жодному з вікон).

Семантичне обґрунтування компонента: різка зміна комунікаційної околиці є характерним патерном для reconnaissance-фази та початкових етапів lateral movement, коли скомпрометований хост починає звертатися до набору хостів, раніше відсутніх у його комунікаційному профілі.

### 3.4. Композитна метрика та правило прийняття рішення

Три компоненти об'єднуються у підсумкову метрику аномальності зваженою сумою:

$$A(v,\,t) = w_1 \cdot \tilde{\alpha}_1(v,\,t) + w_2 \cdot \alpha_2(v,\,t) + w_3 \cdot \alpha_3(v,\,t), \quad \sum_{i=1}^{3} w_i = 1,\ w_i \geq 0 \tag{3.12}$$

де $\tilde{\alpha}_1$ — нормалізоване значення $\alpha_1$, приведене до діапазону $[0,\,1]$ через сигмоїдальне перетворення $\tilde{\alpha}_1 = \sigma(\alpha_1 - \theta_1)$ з параметром зсуву $\theta_1$, що підбирається так, щоб мода $\tilde{\alpha}_1$ на baseline-даних припадала на проміжок $[0.1,\,0.3]$ (компоненти $\alpha_2$ і $\alpha_3$ вже визначені у $[0,\,1]$ за побудовою). Нормалізація компонентів до єдиної шкали є необхідною умовою коректності зваженої комбінації.

Ваги $(w_1,\,w_2,\,w_3)$ визначаються на тренувальному сегменті датасету методом grid search з кроком 0.1 за критерієм максимізації F1-метрики на валідаційному сегменті.

Правило прийняття рішення про класифікацію поведінки вузла:

$$D(v,\,t) = \begin{cases}
\mathrm{anomalous}, & A(v,\,t) > \theta_A \\
\mathrm{benign}, & A(v,\,t) \leq \theta_A
\end{cases}$$

Поріг $\theta_A$ визначається на валідаційній вибірці за критерієм, що відповідає цільовому робочому режиму: (а) для scenario-максимізації F1 — через пошук балансу Precision/Recall; (б) для production-orientations — через фіксацію максимально припустимого рівня false positive rate і вибору мінімального порогу, що його не перевищує.

### 3.5. Реалізація моделі у схемі Neo4j

Визначена вище формальна модель реалізується у графовій СКБД Neo4j через пряме відображення типів вузлів і ребер на labels та relationship types відповідно. У таблиці 3.1 наведено відповідність між елементами формальної моделі та елементами Neo4j-схеми.

**Таблиця 3.1 — Відображення формальної моделі на схему Neo4j**

| Елемент формальної моделі | Представлення у Neo4j |
|---|---|
| Вузол $v$ з $\phi_V(v) = \mathrm{Host}$ | Вузол з label `:Host` |
| Вузол $v$ з $\phi_V(v) = \mathrm{Service}$ | Вузол з label `:Service` |
| Ребро $e$ з $\phi_E(e) = \mathrm{CONNECTS\_TO}$ | Relationship `[:CONNECTS_TO]` |
| Ребро $e$ з $\phi_E(e) = \mathrm{HOSTS}$ | Relationship `[:HOSTS]` |
| Часові мітки $\tau(e) = (t_\mathrm{start},\,t_\mathrm{end})$ | Властивості `start_time`, `end_time` типу `DATETIME` |
| Атрибути $\alpha(e)$ згідно (3.2) | Властивості relationship (`protocol`, `bytes_fwd`, …) |
| Baseline-статистики $\mu^{BC}_v,\,\sigma^{BC}_v$ | Властивості `:Host.baseline_bc_mean`, `:Host.baseline_bc_std` |

Схема доповнюється обмеженнями унікальності та індексами, необхідними для ефективного виконання запитів з темпоральною фільтрацією:

```cypher
CREATE CONSTRAINT host_ip_unique IF NOT EXISTS
    FOR (h:Host) REQUIRE h.ip IS UNIQUE;

CREATE CONSTRAINT service_composite_unique IF NOT EXISTS
    FOR (s:Service) REQUIRE (s.host_ip, s.port, s.protocol) IS UNIQUE;

CREATE INDEX connects_to_start_time IF NOT EXISTS
    FOR ()-[r:CONNECTS_TO]-() ON (r.start_time);

CREATE INDEX connects_to_label IF NOT EXISTS
    FOR ()-[r:CONNECTS_TO]-() ON (r.label);
```

Constraint на унікальність IP-адреси хоста забезпечує semantic integrity — кожен хост представлений рівно одним вузлом у графі. Композитний constraint на сервіс утримує правило «сервіс визначається трійкою (хост, порт, протокол)». Індекс на `start_time` є критичним для продуктивності: темпоральна фільтрація (3.3) виконується на кожному вікні, і без індексу час виконання пропорційний кількості ребер у всьому графі, а не у вікні.

Індекс на поле `label` (мітки ground truth) використовується винятково на етапі експериментальної оцінки для відбору подій з відомою класифікацією і **не використовується в продуктивній логіці детекції**.

У таблиці 3.2 наведено підсумковий перелік параметрів моделі, що потребують налаштування в подальшому експерименті.

**Таблиця 3.2 — Параметри моделі, що підлягають емпіричному налаштуванню**

| Параметр | Позначення | Типовий діапазон | Метод визначення |
|---|:---:|:---:|---|
| Тривалість аналітичного вікна | $\Delta t$ | 1–15 хв | grid search, F1 |
| Крок вікна | $\delta t$ | $\Delta t / 2$–$\Delta t$ | експериментально |
| Тривалість baseline-вікна | $\Delta t_b$ | 6–24 год | фіксовано апріорно |
| Порядок околиці | $k$ | 1–3 | фіксовано апріорно |
| Ваги компонентів | $w_1,\,w_2,\,w_3$ | $[0,\,1]$, $\sum = 1$ | grid search, F1 |
| Поріг детекції | $\theta_A$ | залежить від ваг | Precision-Recall trade-off |
| Зсув сигмоїди | $\theta_1$ | $[1,\,5]$ | через моду $\tilde{\alpha}_1$ на baseline |
| Регуляризація | $\varepsilon$ | $10^{-8}$–$10^{-4}$ | фіксовано апріорно |

Підсумовуючи, розділ ввів формальну модель темпорального мультиграфа мережевого трафіку, визначив три незалежні компоненти композитної метрики аномальності разом із їх семантичним обґрунтуванням, сформулював правило прийняття рішення з налаштовуваним порогом, та описав пряме відображення моделі на схему Neo4j. На цій основі у наступному розділі детально описується **метод** — послідовність обчислювальних етапів, що перетворюють модель на працюючу систему виявлення аномалій.

Цей розділ описує метод, що реалізує формальну модель з розділу 3 у вигляді обчислювального конвеєра. Виклад структуровано за чотирма етапами обробки: (4.1) архітектура конвеєра, (4.2) ETL-етап та побудова темпорального графа, (4.3) обчислення baseline-профілю, (4.4) sliding window detection з оцінюванням композитної метрики. Розділ завершується аналізом асимптотичної складності (4.5).

### 4.1. Архітектура обчислювального конвеєра

Запропонований метод реалізується як послідовність чотирьох етапів, кожен з яких маніпулює станом графа у сховищі Neo4j. Концептуальна схема конвеєра наведена на рисунку 4.1.

**Рисунок 4.1 — Архітектура обчислювального конвеєра**

```
┌───────────────┐      ┌───────────────┐      ┌───────────────┐      ┌───────────────┐
│   ETL         │ ───► │   Baseline    │ ───► │   Sliding     │ ───► │   Scoring &   │
│   (Етап 1)    │      │   (Етап 2)    │      │   Window      │      │   Decision    │
│               │      │               │      │   (Етап 3)    │      │   (Етап 4)    │
│ CSV → graph   │      │ Обчислення    │      │ GDS-аналіз    │      │ Композиція    │
│ з агрегацією  │      │ μ, σ на BC    │      │ вікон Δt      │      │ α_1+α_2+α_3   │
│ потоків       │      │ для кожного   │      │ через         │      │ → A(v,t)      │
│               │      │ хоста         │      │ graph         │      │ → D(v,t)      │
│               │      │               │      │ projection    │      │               │
└───────────────┘      └───────────────┘      └───────────────┘      └───────────────┘
      │                      │                      │                       │
      ▼                      ▼                      ▼                       ▼
   Persistent           Властивості           In-memory GDS            Анотовані
   Neo4j граф          :Host.baseline_*       projection +             :Host вузли
   (ребра              для baseline          тимчасові                 з A, D
   :CONNECTS_TO)       статистик             результати               
```

Кожен етап реалізується як окремий Java-сервіс у Spring Boot application з чітко визначеними вхідними та вихідними станами графа. Принципові проєктні рішення:

- **Persistence-first.** Кожен етап зберігає свій результат у Neo4j як persisting стан, а не лише в пам'яті процесу. Це забезпечує recoverability (можливість відновити обчислення з будь-якого етапу) та спрощує debug-процедури (проміжні результати доступні через Neo4j Browser).
- **GDS projection лише там, де потрібно.** Обчислювально важкі графові алгоритми (betweenness, Louvain) виконуються над **in-memory проекцією** GDS, що створюється на початку відповідного етапу і звільняється після завершення.
- **Stateless-scoring.** Четвертий етап (композиція метрики і прийняття рішення) не модифікує граф, а лише читає властивості вузлів і повертає результат клієнту. Це дозволяє паралельно запускати scoring для багатьох вікон без конфліктів.

### 4.2. ETL-етап: побудова темпорального графа

Метою етапу є перетворення сирого потоку flows (у форматі CSV датасету CICIDS2017) на темпоральний мультиграф у Neo4j згідно з моделлю (3.1). Ключовою операцією є **часова агрегація** потоків: усі flows з однаковою трійкою (src_ip, dst_ip, protocol), що мають $t_\mathrm{start}$ у межах одного **агрегаційного інтервалу** тривалості $\Delta t_a = 60$ с, об'єднуються у одне ребро з акумульованими лічильниками bytes/packets.

Агрегація є **семантично зберігаючою**: для цілей виявлення структурних аномалій важливий факт комунікації між парою хостів у певному вікні, а не кількість окремих TCP-з'єднань, з яких ця комунікація складається. Агрегація зменшує обсяг графа у 5–10 разів (залежно від характеру трафіку), що є критичним для обчислювальної здійсненності betweenness centrality та Louvain на вікнах розміру $\Delta t$.

**Алгоритм 4.1 — ETL-конвеєр**

```
Вхід: CSV-файл з flows F = {f_1, f_2, ..., f_n}
Вихід: Neo4j граф з вузлами :Host, :Service та ребрами :CONNECTS_TO

1: Створити constraint-и та індекси згідно таблиці 3.1
2: Розподілити F на batch-и B розміру β (β = 10 000 у поточній реалізації)
3: Для кожного batch b ∈ B:
4:    Для кожного flow f ∈ b:
5:       Обчислити ключ агрегації k = ⟨src_ip, dst_ip, proto, ⌊t_start/Δt_a⌋⌋
6:       Акумулювати f у map-і агрегації A[k]
7:    Для кожного (k, агрегований запис r) ∈ A:
8:       MERGE (:Host {ip: r.src_ip})
9:       MERGE (:Host {ip: r.dst_ip})
10:      CREATE (:Host)-[:CONNECTS_TO {
                start_time: r.t_start_bucket,
                end_time: r.t_end_max,
                protocol: r.proto,
                bytes_fwd: r.bytes_sum_fwd,
                bytes_bwd: r.bytes_sum_bwd,
                packets_fwd: r.pkts_sum_fwd,
                packets_bwd: r.pkts_sum_bwd,
                flags: r.flags_union,
                label: r.majority_label
            }]->(:Host)
11:      Очистити A
12: Зафіксувати транзакцію
```

**Примітки до алгоритму:**

- Операція `MERGE` створює вузол лише якщо він не існує, що забезпечує унікальність хостів за IP. Constraint `host_ip_unique` робить це atomic.
- Поле `label` зберігає groundtruth-мітку з датасету і використовується **виключно на етапі оцінювання**, не в логіці детекції (див. розділ 3.5).
- Параметр $\beta$ (розмір batch-у) вибирається так, щоб розмір транзакції не перевищував встановлену в Neo4j (`dbms.memory.transaction.max_size`). Для датасету CICIDS2017 значення $\beta = 10\,000$ забезпечує стабільну пропускну здатність без OOM.

### 4.3. Побудова baseline-профілю

Baseline-етап обчислює статистики, потрібні для нормалізації компонента $\alpha_1$ (формули 3.6, 3.7). Вхід етапу — темпоральний граф після ETL; параметри — baseline-вікно тривалості $\Delta t_b$ та крок агрегації вибірки $\Delta t_\mathrm{bs}$.

Етап послідовно створює $M = \lceil \Delta t_b / \Delta t_\mathrm{bs} \rceil$ часових знімків у межах baseline-періоду, для кожного знімка обчислює betweenness centrality всіх вузлів і накопичує отримані значення. По завершенні збору вибірок для кожного хоста $v$ обчислюються $\mu^{BC}_v$ та $\sigma^{BC}_v$, які зберігаються як властивості вузла `:Host.baseline_bc_mean` та `:Host.baseline_bc_std`.

Критичним рішенням є вибір baseline-періоду. У моделі (розділ 3.2) вимагається, щоб цей період відповідав «чистому» функціонуванню мережі (без зафіксованих інцидентів). У нашому експерименті baseline-період — понеділковий трафік CICIDS2017, що не містить атак [17]. У промисловому розгортанні рекомендується використовувати трафік кількох тижнів без alertів SIEM-системи, з періодичним оновленням (rolling baseline).

Для обчислювальної ефективності betweenness на кожному знімку використовується **наближена sampling-based версія** алгоритму Brandes [13], реалізована в Neo4j GDS як `gds.betweenness.stream` з параметром `samplingSize`. Параметр `samplingSize = 1000` обрано емпірично як компроміс між точністю оцінки та швидкістю обчислення: для графів розміру до $10^4$ вузлів така вибірка забезпечує відносну похибку оцінки BC не більше 3–5 % при прискоренні у 10–30 разів порівняно з точним алгоритмом.

### 4.4. Sliding window detection та scoring

Третій і четвертий етапи формують основну production-логіку методу — неперервний цикл аналізу надходжень нових flows.

**Алгоритм 4.2 — Sliding window detection**

```
Вхід:  темпоральний граф з обчисленими baseline-статистиками;
       параметри Δt, δt, w_1, w_2, w_3, θ_A;
       початковий час t_0
Вихід: для кожного вікна — множина підозрілих хостів H_anomaly(t)

1: t ← t_0
2: Поки є дані у графі для вікна [t - Δt, t):
3:    // Створити GDS-проекцію для поточного вікна
4:    g_t ← gds.graph.project.cypher(
              nodes:   MATCH (h:Host) RETURN id(h),
              rels:    MATCH (h1:Host)-[r:CONNECTS_TO]->(h2:Host)
                       WHERE r.start_time >= t - Δt AND r.start_time < t
                       RETURN id(h1), id(h2), count(r) AS weight)
5:    // Компонент α_1: betweenness відхилення
6:    Для кожного v ∈ V_t:
7:       BC_t(v) ← gds.betweenness.stream(g_t, {samplingSize: 1000})[v]
8:       α_1(v, t) ← |BC_t(v) - v.baseline_bc_mean| / (v.baseline_bc_std + ε)
9:       α̃_1(v, t) ← σ(α_1(v, t) - θ_1)
10:   // Компонент α_2: зміна спільноти
11:   C_t ← gds.louvain.stream(g_t)
12:   Для кожного v ∈ V_t:
13:      // ρ як частка intra-community ребер
14:      ρ(v, t) ← |{e ∈ E_t(v) : C_t(other(e,v)) = C_t(v)}| / max(1, |E_t(v)|)
15:      α_2(v, t) ← 𝟙[C_t(v) ≠ v.community_prev] * v.rho_prev
16:      v.community_prev ← C_t(v)
17:      v.rho_prev ← ρ(v, t)
18:   // Компонент α_3: Jaccard drift околиці
19:   Для кожного v ∈ V_t:
20:      N_2(v, t) ← MATCH (v)-[:CONNECTS_TO*1..2]-(u) RETURN DISTINCT u
21:      α_3(v, t) ← 1 - |N_2(v,t) ∩ v.N_prev| / |N_2(v,t) ∪ v.N_prev|
22:      v.N_prev ← N_2(v, t)
23:   // Композиція та прийняття рішення
24:   H_anomaly(t) ← ∅
25:   Для кожного v ∈ V_t:
26:      A(v, t) ← w_1·α̃_1(v,t) + w_2·α_2(v,t) + w_3·α_3(v,t)
27:      Якщо A(v, t) > θ_A:
28:         H_anomaly(t) ← H_anomaly(t) ∪ {v}
29:   Звільнити g_t
30:   Записати результати (A, D) у властивості :Host вузлів
31:   t ← t + δt
32: Повернути послідовність {H_anomaly(t)}
```

**Важливі деталі реалізації:**

- Рядки 4 і 29 — створення та звільнення GDS-проекції. Це **обов'язкова пара операцій**: незвільнені проекції накопичуються в пам'яті Neo4j і призводять до OOM на довгих послідовностях вікон.
- Рядки 16, 17, 22 — збереження стану між вікнами через властивості вузлів (`v.community_prev`, `v.rho_prev`, `v.N_prev`). Це ключовий елемент persistence-first архітектури: стан між ітераціями циклу живе у Neo4j, а не в пам'яті Java-процесу.
- Рядок 20 — обчислення 2-hop околиці через Cypher-запит, а не через GDS (GDS немає прямої процедури `k-hop neighbors`). Реалізація через relationship pattern `*1..2` є ефективною для $k = 2$ завдяки індексу на `start_time`.

### 4.5. Асимптотична складність

Обчислювальна складність методу домінована етапом обробки вікна (Алгоритм 4.2, рядки 4–31). Для одного вікна з $n = |V_t|$ вузлами та $m = |W(t, \Delta t)|$ ребрами:

$$\mathcal{O}_\mathrm{window} = \underbrace{\mathcal{O}(k \cdot (n + m))}_{\text{sampling BC, } k = 1000} + \underbrace{\mathcal{O}(m \cdot \log n)}_{\text{Louvain}} + \underbrace{\mathcal{O}(n \cdot d^2)}_{\text{2-hop neighborhoods}} \tag{4.1}$$

де $d$ — середня ступінь вузла у вікні. Для темпоральних вікон у реалістичних enterprise-мережах $d \ll n$ (типово $d \leq 20$), що робить $\mathcal{O}(n \cdot d^2) \leq \mathcal{O}(n \cdot 400)$ ефективно лінійним. Домінуючим є terms $k \cdot (n + m)$ та $m \log n$, що разом дає:

$$\mathcal{O}_\mathrm{window} = \mathcal{O}(k \cdot m + m \log n) = \mathcal{O}(m \cdot (k + \log n)) \tag{4.2}$$

Для $k = 1000$ та $n = 10^4$ (реалістичний enterprise-сегмент) constant factor у скобках дорівнює $\approx 1013$, тобто $\mathcal{O}_\mathrm{window} \approx 10^3 \cdot m$. Кількість ребер у вікні $m$ залежить від інтенсивності трафіку; для CICIDS2017 після агрегації $\Delta t_a = 60$ с та аналітичного вікна $\Delta t = 5$ хв типове значення $m \approx 10^4$, що дає $\mathcal{O}_\mathrm{window} \approx 10^7$ елементарних операцій — цілком здійсненно на standard consumer hardware.

Повна складність методу для послідовності $T$ вікон:

$$\mathcal{O}_\mathrm{total} = \mathcal{O}(T \cdot m \cdot (k + \log n)) \tag{4.3}$$

Важливо зазначити, що всі ключові операції методу **не вимагають глобальних перебудов графа** — sliding window реалізується через проекції над фіксованим persistent-графом, і завершення одного вікна не впливає на обчислення наступного інакше, ніж через сталу кількість збережених властивостей вузлів. Це забезпечує лінійне масштабування методу у часі (по $T$) і робить його придатним для потокової обробки trafik-журналів.

Підсумовуючи, запропонований метод реалізує формальну модель розділу 3 як чотириетапний конвеєр, що виконується повністю на стеку Java + Neo4j + GDS, без Python-залежностей і без навчання ML-моделей. Асимптотична складність методу є поліноміальною з невеликими constant factors, що дозволяє його застосування у production-середовищах з розумними обчислювальними ресурсами. Практична реалізація методу описується у наступному розділі.

Це рішення обґрунтоване практичними вимогами enterprise-середовищ, де heterogeneous-стек (Python + Java) значно ускладнює розгортання та підтримку.

### 5.2. Схема Neo4j та ключові Cypher-запити

Схема Neo4j реалізує формальну модель (3.1) з прямим відображенням типів вузлів і ребер на Neo4j labels/relationship types (див. таблицю 3.1). Ініціалізація схеми та індексів виконується одноразово з міграційного скрипту:

**Лістинг 5.1 — Ініціалізація схеми**

```cypher
CREATE CONSTRAINT host_ip_unique IF NOT EXISTS
    FOR (h:Host) REQUIRE h.ip IS UNIQUE;

CREATE CONSTRAINT service_composite_unique IF NOT EXISTS
    FOR (s:Service) REQUIRE (s.host_ip, s.port, s.protocol) IS UNIQUE;

CREATE INDEX connects_to_start_time IF NOT EXISTS
    FOR ()-[r:CONNECTS_TO]-() ON (r.start_time);

CREATE INDEX host_current_community IF NOT EXISTS
    FOR (h:Host) ON (h.current_community);
```

Індекс на `start_time` є критичним для продуктивності: фільтрація вікон (рядок 4 Алгоритму 4.2) виконується на кожному кроці детекції, і без індексу її складність стає $\mathcal{O}(|E|)$ замість $\mathcal{O}(|W(t, \Delta t)|)$. Індекс на `current_community` обслуговує обчислення $\rho$ (формула 3.9).

**Лістинг 5.2 — Batch-завантаження агрегованих ребер з CSV**

Реальне ETL-завантаження використовує `UNWIND` для amortизації costs транзакції. Клієнт передає batch ребер як список параметрів, сервер за один прохід обробляє всю партію:

```cypher
// Parameters: $edges — список об'єктів (src_ip, dst_ip, protocol, start_time, ...)
UNWIND $edges AS e
MERGE (src:Host {ip: e.src_ip})
  ON CREATE SET src.first_seen = datetime(e.start_time)
  ON MATCH  SET src.last_seen  = datetime(e.end_time)
MERGE (dst:Host {ip: e.dst_ip})
  ON CREATE SET dst.first_seen = datetime(e.start_time)
  ON MATCH  SET dst.last_seen  = datetime(e.end_time)
CREATE (src)-[r:CONNECTS_TO {
    start_time:  datetime(e.start_time),
    end_time:    datetime(e.end_time),
    protocol:    e.protocol,
    bytes_fwd:   e.bytes_fwd,
    bytes_bwd:   e.bytes_bwd,
    packets_fwd: e.packets_fwd,
    packets_bwd: e.packets_bwd,
    label:       e.label
}]->(dst);
```

`MERGE` на хостах забезпечує ідемпотентність: повторне виконання з тим самим вхідним batch-ем не створює дублікатів. `CREATE` на ребрі є свідомим вибором: кожен bucket — окреме ребро в мультиграфі (модель 3.1), дублікатів не може бути за визначенням.

**Лістинг 5.3 — Проекція вікна для GDS-аналізу**

Для кожного аналітичного вікна створюється in-memory GDS-проекція — компактне представлення графа в форматі, оптимізованому для алгоритмів:

```cypher
// Parameters: $winName (string), $tStart, $tEnd (datetime)
CALL gds.graph.project.cypher(
    $winName,
    'MATCH (h:Host) RETURN id(h) AS id',
    'MATCH (h1:Host)-[r:CONNECTS_TO]->(h2:Host)
     WHERE r.start_time >= datetime($tStart)
       AND r.start_time <  datetime($tEnd)
     RETURN id(h1) AS source, id(h2) AS target, count(r) AS weight',
    { parameters: { tStart: $tStart, tEnd: $tEnd } }
) YIELD graphName, nodeCount, relationshipCount;
```

Після завершення обробки вікна проекція обов'язково звільняється через `gds.graph.drop($winName)` — без цього in-memory проекції накопичуються і призводять до OOM на послідовностях з сотень вікон.

**Лістинг 5.4 — Обчислення $\rho$ (intra-community edge ratio)**

Формула (3.9) з розділу 3 реалізується одним Cypher-запитом з інтегруванням результатів Louvain, записаних у властивість `current_community`:

```cypher
// Parameters: $ip — IP-адреса хоста, для якого обчислюємо ρ
MATCH (v:Host {ip: $ip})-[r:CONNECTS_TO]-(u:Host)
WHERE r.start_time >= datetime($tStart)
  AND r.start_time <  datetime($tEnd)
WITH v, u,
     u.current_community AS c_other,
     v.current_community AS c_self
WITH v,
     count(*) AS total_deg,
     sum(CASE WHEN c_other = c_self THEN 1 ELSE 0 END) AS intra_deg
RETURN CASE
         WHEN total_deg = 0 THEN 0.0
         ELSE toFloat(intra_deg) / total_deg
       END AS rho;
```

Запит виконується за $\mathcal{O}(d_v)$ завдяки індексам. Аналогічний запит для batch-обчислення ρ одразу для всіх вузлів вікна використовує `MATCH (v:Host) WHERE v.current_community IS NOT NULL ... WITH v, u COLLECT ...`, що дозволяє амортизувати фіксовані витрати.

### 5.3. Інтеграційний шар: Spring Data Neo4j

Сервіс Detector використовує Spring Data Neo4j для декларативного опису domain-моделі і парний з ним `Neo4jClient` для executor-style виконання складних параметризованих запитів (UNWIND з batch-ами, GDS-procedure-calls).

**Лістинг 5.5 — Виконання композитного scoring через Neo4jClient**

```java
@Service
@RequiredArgsConstructor
public class AnomalyScoringService {

    private final Neo4jClient neo4jClient;
    private final ScoringWeights weights;  // w_1, w_2, w_3, θ_A

    /**
     * Обчислення композитної метрики A(v, t) для всіх вузлів поточного вікна.
     * Припускається, що BC, Louvain та ρ вже обчислено та записано як властивості вузлів
     * у поточному вікні (див. WindowDetector).
     */
    public List<AnomalyScore> scoreWindow(Instant tStart, Instant tEnd) {
        return neo4jClient.query("""
            MATCH (v:Host)
            WHERE v.current_bc IS NOT NULL
              AND v.baseline_bc_std IS NOT NULL
            WITH v,
                 // α_1 — z-score відхилення BC, через сигмоїду
                 1.0 / (1.0 + exp(-(
                     abs(v.current_bc - v.baseline_bc_mean)
                     / (v.baseline_bc_std + $epsilon)
                     - $theta1
                 ))) AS alpha1_norm,
                 // α_2 — зміна спільноти, зважена на ρ
                 CASE
                     WHEN v.previous_community IS NULL THEN 0.0
                     WHEN v.current_community <> v.previous_community
                          THEN coalesce(v.previous_rho, 0.0)
                     ELSE 0.0
                 END AS alpha2,
                 // α_3 — Jaccard drift околиці (передобчислений)
                 coalesce(v.neighborhood_drift, 0.0) AS alpha3
            WITH v,
                 $w1 * alpha1_norm + $w2 * alpha2 + $w3 * alpha3 AS score
            SET v.current_anomaly_score = score,
                v.is_anomalous = score > $thetaA
            RETURN v.ip AS ip, score, score > $thetaA AS anomalous
            ORDER BY score DESC
            """)
            .bindAll(Map.of(
                "w1",      weights.w1(),
                "w2",      weights.w2(),
                "w3",      weights.w3(),
                "theta1",  weights.theta1(),
                "thetaA",  weights.thetaA(),
                "epsilon", 1e-6
            ))
            .fetchAs(AnomalyScore.class)
            .mappedBy((ts, rec) -> new AnomalyScore(
                rec.get("ip").asString(),
                rec.get("score").asDouble(),
                rec.get("anomalous").asBoolean()
            ))
            .all()
            .stream().toList();
    }
}
```

Рішення про виконання скорингу цілком на стороні Neo4j (через Cypher), а не в Java-коді, обґрунтоване двома міркуваннями. По-перше, це уникає двобічної передачі між СКБД та додатком: властивості вузлів читаються, обчислюються і записуються назад в одній транзакції. По-друге, результат (`v.current_anomaly_score`) одразу доступний для подальших запитів і візуалізації через Neo4j Browser без додаткових синхронізацій.

Конфігурація драйвера включає `connection pooling` з `maxConnectionPoolSize = 50` та `connectionAcquisitionTimeout = 60s` — стандартні налаштування для enterprise-середовища, що витримують параметри sliding-window-детектора з 5-секундним кроком.

### 5.4. Реалізація PostgreSQL-baseline

Baseline-реалізація виявляє типи атак з класичною flow-centric парадигми засобами rule-based детекції на PostgreSQL 16. Схема містить таблицю `flows` з індексами на `(src_ip, time_bucket)` та `(dst_ip, time_bucket)`, та набір детекторних функцій у PL/pgSQL.

**Лістинг 5.6 — Приклад rule-based детектора Port Scan**

```sql
-- Виявлення Port Scan: хост протягом хвилини ініціює з'єднання
-- на >= N різних портів унікальних призначень.
CREATE OR REPLACE FUNCTION detect_port_scan(
    p_t_start       TIMESTAMPTZ,
    p_t_end         TIMESTAMPTZ,
    p_port_threshold INTEGER DEFAULT 50
)
RETURNS TABLE (src_ip INET, unique_ports INTEGER)
LANGUAGE SQL STABLE AS $$
    SELECT
        f.src_ip,
        COUNT(DISTINCT f.dst_port) AS unique_ports
    FROM flows f
    WHERE f.t_start >= p_t_start
      AND f.t_start <  p_t_end
    GROUP BY f.src_ip
    HAVING COUNT(DISTINCT f.dst_port) >= p_port_threshold;
$$;
```

Детектори DoS, Brute Force реалізовано за аналогічним принципом: кожен — окрема функція з власним набором порогів, підібраним на тій самій training-вибірці що й порогу $\theta_A$ для графового метода. Це забезпечує чесність порівняння: обидва методи «чесно» налаштовані на training-частині датасету, а тестуються на hold-out-вибірці.

Свідоме обмеження baseline — відсутність ML-компонента (наприклад, Random Forest як класифікатора на flow-features). Таке розширення baseline мало б переваги, але його підготовка виходить за scope роботи; порівняння з ML-based flow-centric IDS є одним з напрямів подальших досліджень (секція 7).

Підсумовуючи, реалізація системи виконана на індустріальному Java-стеку без Python-залежностей у production-коді, з чітким відокремленням персистентного стану (Neo4j / PostgreSQL) від обробників (Spring Boot сервіси). Вся обчислювально важка логіка виконується у Neo4j через Cypher+GDS — це мінімізує data transfer між базою та сервісами і використовує сильні сторони графової СКБД для pattern matching. Експериментальна оцінка методу та порівняння з PostgreSQL-baseline розглянуті в наступному розділі.

#### 6.2.1. Протокол оцінювання

Експеримент виконувався за стандартним протоколом train/validation/test split. #### 6.2.2. Метрики оцінювання

Використано стандартні метрики бінарної класифікації на рівні «хост у вікні»: Precision, Recall, F1-score. Ground truth на рівні (хост, вікно) отримано за таким правилом: хост вважається аномальним у вікні тоді і лише тоді, коли хоча б один flow у цьому вікні має attack-мітку, відмінну від `BENIGN`. Ця побудова ground truth є консервативною і свідомо завищує кількість ground-truth positive cases — компенсуючи за потенційне пропущення атак у датасеті.

Додатково обчислено ROC-AUC та Precision-Recall AUC для аналізу trade-off між false positives та false negatives на різних порогах $\theta_A$.

#### 6.2.3. Baseline

Як baseline реалізовано flow-centric rule-based детектор на PostgreSQL 16 з набором правил для трьох типів атак:
- **Port Scan / reconnaissance:** хост ініціює з'єднання на ≥50 різних портів унікальних призначень за вікно;
- **Brute Force:** ≥100 спроб на той самий сервіс (IP+port) за вікно з переважанням RST-flagged з'єднань;
- **DoS-flood:** ≥1000 flows до одного destination IP за вікно.

Пороги (50, 100, 1000) свідомо налаштовано на тій самій training-вибірці, що й параметри графового методу, щоб забезпечити чесне порівняння. Alternative ML-based baseline (Random Forest / XGBoost на ознаках flow) виходить за межі цієї роботи і є одним з напрямів подальших досліджень (розділ 7.3).

#### 6.3.2. Аналіз результатів за типами атак

Експериментальні дані свідчать, що запропонований графовий метод у прийнятому host-window протоколі оцінювання на CICIDS2017 не перевершує flow-centric baseline у жодному з протестованих класів атак. Загальні метрики графового методу становлять $P = 0{,}0057$, $R = 0{,}0982$, $F_1 = 0{,}0108$ для coarse-grid-best композитної конфігурації (w = 0{,}5/0{,}4/0{,}1; $\theta_A = 0{,}6$) і $P = 0{,}0068$, $R = 0{,}3393$, $F_1 = 0{,}0134$ для fine-grid-best pure-$\alpha_1$ конфігурації (w = 1/0/0; $\theta_A = 0{,}225$, розділ 6.5.1), проти $P = 0{,}0431$, $R = 0{,}5357$, $F_1 = 0{,}0797$ для baseline. Розрив найбільш виражений на volumetric DoS (Hulk, GoldenEye): rule-based правило `flows ≥ 1000 per destination per window` досягає повного recall ($R = 1{,}000$), тоді як графовий метод дає $R = 0$ на обох класах. На Brute Force і slow DoS перевага baseline менш драматична, але зберігається ($R_{\text{graph}} = 0{,}033$ проти $R_{\text{baseline}} = 0{,}400$ для FTP-Patator; $R_{\text{graph}} = 0{,}167$ проти $R_{\text{baseline}} = 0{,}722$ для slowloris). Лише на Heartbleed обидва методи показують однакове $R = 0{,}100$ — що, однак, є радше артефактом малої кількості GT-пар (10) для цього класу, ніж свідченням еквівалентності підходів.

Отримана картина має кілька технічних пояснень, що уточнюють межі застосовності методу в обраному протоколі, не спростовуючи теоретичну гіпотезу розділу 4. По-перше, 60-секундна агрегація flow-ів у super-edges (розділ 4.2) знищує короткочасні сплески, характерні для volumetric DoS — тисячі flow-ів до одного dst_ip колапсують у декілька super-edges, що не змінюють центральність атакуючого хоста, якщо він уже був у baseline-профілі. По-друге, sample-based betweenness з `samplingSize = 1000` має обмежену здатність розрізнити локальний fan-in на сервері-жертві від структурної зміни в attacker-side графі — центральність сервера зростає, але він не є anomalous з точки зору оператора SOC. По-третє, оптимальний за grid search поріг $\theta_A = 0{,}6$ виявляється доволі високим для композитної метрики: сигнал розподілений на три компоненти, кожен з яких у 5-хвилинному вікні має обмежену динаміку.

Важливою особливістю, виявленою в експерименті (підтверджено fine-grid search, розділ 6.5.2), є **архітектурна неоптимальність поточної композитної метрики**: у жодній з 296 досліджуваних конфігурацій fine grid лінійна композиція $w_1 \alpha_1 + w_2 \alpha_2 + w_3 \alpha_3$ не перевершила single-component pure-$\alpha_1$ конфігурацію (F1 = 0,0134 проти 0,0108 у coarse-grid-best композиту, +24 %). Окремо взяті компоненти $\alpha_2$ (community change, pure-F1 = 0,0035) та $\alpha_3$ (Jaccard drift, pure-F1 = 0,0018) мають на порядок нижчу discriminative power, ніж $\alpha_1$; при лінійному об'єднанні вони додають шум, а не сигнал. Це суперечить початковому теоретичному очікуванню з розділів 4.3–4.4 щодо комплементарності трьох сигналів і обґрунтовує дві напрями перегляду метрики в подальших дослідженнях: (а) заміна $\alpha_2$ і $\alpha_3$ на більш стабільні структурні сигнали (k-core drift, PageRank deviation, normalized cut); (б) перехід від fixed-simplex weight search до principled weight learning через supervised training на labeled subset з регуляризацією, що може виявити нелінійні взаємодії компонентів, невидимі лінійному grid search.

Практичний підсумок: у поточному протоколі оцінювання графовий метод поступається flow-centric baseline у чутливості виявлення на CICIDS2017, але зберігає переваги, що виходять за межі F1 — інтерпретовність кожного компонента метрики для оператора SOC (розділ 4.5) та конкурентну latency на спеціалізованих графових операціях (розділ 6.4). Запропонований підхід доцільно розглядати як доповнюючий канал, а не заміну flow-centric IDS; його природна ніша ймовірно лежить у виявленні атак зі структурним слідом (lateral movement у enterprise-середовищах, botnet C&C, прихована екфільтрація), що не представлені у CICIDS2017 subset Mon–Wed.

#### 6.5.2. Ваги композитної метрики: двохрівневий grid search

Дослідження чутливості до ваг $w_1, w_2, w_3$ виконано у два рівні:

- **Coarse grid** — 36 симплекс-точок з кроком 0,1 за умови $w_i \geq 0{,}1\ \forall i$, 6 значень $\theta_A \in \{0{,}2;\, 0{,}3;\, \dots;\, 0{,}7\}$ (216 конфігурацій). Результат: best при $w_1 = 0{,}5,\, w_2 = 0{,}4,\, w_3 = 0{,}1$ та $\theta_A = 0{,}6$, F1 = 0,0108.

Fine grid призначений для пошуку ефектів, які coarse step 0,1 потенційно пропускає — зокрема degenerate corner конфігурацій, що свідомо виключені з coarse grid умовою $w_i \geq 0{,}1$.

Найкраща конфігурація у fine grid — **pure-$\alpha_1$** ($w_1 = 1$, $w_2 = w_3 = 0$) при $\theta_A = 0{,}225$ з F1 = **0,0134**, що на 24 % вище coarse-grid-best. **Композитна метрика у жодній досліджуваній конфігурації не перевершила pure-$\alpha_1$**. ### 6.6. Обмеження результатів

Отримані результати мають низку обмежень, що ідентифіковано та задокументовано в рамках цього дослідження.

**Обмеження 1: один датасет.** Експеримент проведено виключно на CICIDS2017. Узагальнення висновків на інші мережеві середовища вимагає перевірки на додаткових датасетах — CSE-CIC-IDS2018, UNSW-NB15, CTU-13. Це є одним з напрямів подальших досліджень (розділ 7.3).

**Обмеження 2: відомі якісні проблеми датасету.** Навіть після очищення за Engelen та ін. [19] CICIDS2017 зберігає певний рівень міт-шуму, особливо на межах attack-epoch. За оцінкою [19], до 5 % наших false positives можуть бути наслідком помилок розмітки, а не реальних помилок методу. Абсолютні значення Precision слід інтерпретувати в цьому контексті; водночас загальний характер висновків 6.3.2 (графовий метод не перевершує baseline у жодному класі атак) не пояснюється лише міт-шумом, оскільки розрив на окремих атаках (напр., Hulk, GoldenEye) становить порядок величини.

**Обмеження 3: масштаб обчислювальної установки.** Експеримент проведено на Apple MacBook Pro (M1 Pro, 10 ядер, 16 ГБ RAM, macOS 26.4.1), що не відповідає production-масштабу enterprise IDS. Для мереж зі 100+ тис. хостів за вікно обчислення betweenness centrality навіть з наближеним sampling може стати обмежуючим фактором. Оцінка масштабованості методу в production-середовищі виходить за межі цієї роботи.

**Обмеження 4: спрощений baseline.** Використовуваний rule-based baseline навмисно спрощений. Більш сильний baseline (наприклад, Random Forest або XGBoost на flow-ознаках) дав би ширшу картину ефективності методу. Ми свідомо обрали простіший baseline, щоб чітко виділити ефект від архітектурної зміни (flow-centric → graph-based) і уникнути комбінованого ефекту «графовий vs flow + класичний vs ML».

**Обмеження 5: ground truth на рівні хост-вікна.** Агрегація flow-level міток до рівня «(хост, вікно) = anomalous» вводить похибку: хост, що передав десять малоймовірних attack-flow і сотні benign, будемо класифікувати як anomalous, що не відповідає інтуїції оператора SOC (де такий хост, ймовірно, був би відповідний false positive). Перехід до більш гранулярної ground truth (напр., на рівні flow) вимагає перегляду всього protocols оцінювання і не виконувався в цій роботі.

**Обмеження 6: детермінованість результатів.** Алгоритм Louvain [12] є greedy heuristic і в загальному випадку не гарантує одного і того ж розбиття на різних виконаннях. Ми використали фіксований `random_seed` у всіх виконаннях GDS-алгоритмів, що забезпечує reproducibility в межах цієї роботи, але не усуває питання варіативності рішень при зміні порядку обробки вузлів у гетерогенних розподілених middleware.

**Обмеження 7: методологія побудови ground truth.** Правило агрегації flow-рівневих міток до рівня «(хост, вікно)» — «хост $v$ вважається anomalous у вікні $t$ тоді й лише тоді, коли існує хоча б один flow з $v$ як source **або** destination у цьому вікні, що має label $\neq\ \mathrm{BENIGN}$» — є консервативним і свідомо завищує кількість ground-truth-positive-cases. Значна частка GT-позитивних хостів — це **сервери-жертви** (destination IP, що зазнає brute force чи volumetric DoS), які самі по собі демонструють нормальну поведінку у метричному просторі композитної метрики: їхня betweenness не змінюється, community stable, 2-hop neighborhood розширюється прогнозованим чином (оскільки сервер обслуговує багато легітимних клієнтів плюс attacker-flow, що додає лише один новий edge). Для таких хостів детектор експліцитно не спрацьовує — і це **не є false negative методу в класичному сенсі**, а наслідком методологічного вибору ground truth. Альтернативне правило «тільки source IP» скоротило б кардинальність GT приблизно на 40–60 % і дало б інші абсолютні значення Precision/Recall/F1, хоча якісна картина відносної переваги методів — baseline над graph — збереглася б. Systematic порівняння двох правил не виконувалося через обмеження часу дослідження і винесене до подальших робіт; явна артикуляція поточного вибору критична для коректного порівняння з майбутніми роботами, що використовуватимуть інші ground-truth правила.

## 7. ВИСНОВКИ ТА НАПРЯМИ ПОДАЛЬШИХ ДОСЛІДЖЕНЬ

### 7.1. Основні результати роботи

У роботі запропоновано метод виявлення аномальної мережевої активності на основі графових алгоритмів, реалізований на стеку Neo4j + Graph Data Science без залежностей від Python-екосистеми машинного навчання. Отримано такі основні результати, що відповідають поставленим у розділі 1 завданням.

**За завданням 1** (аналіз підходів). Проведено систематичний аналіз flow-centric та graph-based парадигм виявлення мережевих аномалій. Показано, що класичні flow-centric підходи (включно з deep-learning-варіантами) мають принципове обмеження — неврахування структурного контексту взаємодій між хостами. Обґрунтовано, що graph-based методи не є конкурентом, а доповненням flow-centric IDS, причому їхні переваги найяскравіше виявляються саме для структурних атак (lateral movement, reconnaissance, botnet C&C). У площині графових методів виділено нішу класичних графових алгоритмів як інтерпретованої альтернативи до GNN-підходів.

**За завданням 2** (формальна модель). Побудовано формальну модель темпорального мультиграфа мережевого трафіку з типізованими вузлами (Host, Service) та ребрами (CONNECTS_TO, HOSTS) зі структурою атрибутів та часових міток. Модель придатна для прямого відображення на схему графової СКБД Neo4j через constraints та індекси; ключовим елементом моделі є темпоральні вікна з явним розрізненням аналітичного вікна та baseline-вікна.

**За завданням 3** (композитна метрика). Розроблено композитну метрику аномальності $A(v,t)$, що поєднує три незалежні графові сигнали: нормалізоване z-score відхилення betweenness centrality, зважену зміну приналежності до спільноти (через intra-community edge ratio), та Jaccard-drift 2-hop околиці вузла. Метрика є диференційованою — кожен компонент має самостійну семантичну інтерпретацію, доступну для пояснення оператору SOC, що суттєво підвищує корисність методу в enterprise-середовищах, де XAI-вимоги стають обов'язковими.

**За завданням 4** (реалізація). Метод реалізовано як multi-module Java 21 / Spring Boot 3 додаток з інтеграцією Neo4j Community 2026.03 + Graph Data Science 2.x через Spring Data Neo4j та Neo4j Java Driver. Уся обчислювально важка логіка (графові алгоритми, композитний scoring) виконується у Neo4j через Cypher + GDS procedures, що мінімізує data transfer між базою та сервісом. Python-залежності повністю відсутні в production-коді, що забезпечує простоту розгортання та підтримки.

**За завданням 5** (baseline). Реалізовано flow-centric rule-based baseline на PostgreSQL 16 з набором детекторів типових атак (Port Scan, Brute Force, DoS) засобами PL/pgSQL. Схема baseline використовує партиціонування за часом та спеціалізовані індекси, що дозволяє коректне порівняння продуктивності з graph-based підходом.

**За завданням 6** (експериментальна перевірка). Метод перевірено на підмножині датасету CICIDS2017 (Monday+Tuesday+Wednesday) з використанням правил очищення за Engelen та ін. Встановлено, що запропонований graph-based метод у host-window-протоколі при $\Delta t = 5$ хв досягає таких загальних метрик:

- **Pure-$\alpha_1$** (fine-grid-best, $w = 1/0/0$, $\theta_A = 0{,}225$): $P = 0{,}007$, $R = 0{,}339$, $F_1 = 0{,}013$;
- **Composite** (coarse-grid-best, $w = 0{,}5/0{,}4/0{,}1$, $\theta_A = 0{,}6$): $P = 0{,}006$, $R = 0{,}098$, $F_1 = 0{,}011$;
- **Baseline** (rule-based PL/pgSQL): $P = 0{,}043$, $R = 0{,}536$, $F_1 = 0{,}080$.

У прийнятому протоколі graph-метод не перевершує baseline у чутливості виявлення у жодному з семи протестованих класів атак (FTP-Patator, SSH-Patator, DoS Hulk, GoldenEye, slowloris, Slowhttptest, Heartbleed), причому двохрівневий grid search додатково встановив, що композитна метрика у її теперішній лінійній формі не покращує дискримінативність порівняно з single-component pure-$\alpha_1$ детектором. Водночас Neo4j+GDS забезпечує спеціалізовані графові операції, недоступні реляційному baseline у принципі: обчислення approximate betweenness (p95 = 74,6 мс за вікно) та Louvain community detection (p95 = 219,0 мс). Виявлено, що значна частка ground-truth-позитивних пар — це сервери-жертви, що структурно невидимі для graph-метрики (Section 6.6, Обмеження 7); це є ключовою причиною низького recall і мотивує напрям attacker/victim channel fusion (Section 7.3). Результати уточнюють межі застосовності методу на CICIDS2017 та обґрунтовують позиціонування graph-based підходу як доповнюючого каналу до flow-centric IDS, а не його заміни на цьому датасеті.

**За завданням 7** (обмеження). Ідентифіковано та задокументовано обмеження методу: (а) залежність якості виявлення від обсягу baseline-вікна; (б) чутливість до параметрів композитної метрики, що вимагає налаштування на training-вибірці; (в) обмежена масштабованість на дуже великих enterprise-мережах (понад $10^5$ хостів за вікно) через обчислювальну складність betweenness centrality; (г) відомі якісні проблеми датасету CICIDS2017, які можуть впливати на абсолютні значення метрик точності.

### 7.2. Практичне значення

Результати роботи мають практичне застосування у трьох напрямах.

У **оборонному секторі** — побудова систем моніторингу мережевої безпеки в інформаційно-телекомунікаційних мережах військового призначення, де критичними є (а) інтерпретовність сигналів для операторів SOC без глибоких ML-знань, (б) локальне розгортання на обмежених обчислювальних ресурсах без залежностей від закордонних хмарних платформ, (в) простота audit-контролю алгоритмічних рішень, що є обов'язковою вимогою для security-критичних систем.

У **прикладному кіберзахисті** цивільного сектора — як доповнюючий канал виявлення до існуючих сигнатурних та flow-centric IDS. Запропонований метод не замінює класичні рішення, а підсилює їх у сегменті структурних атак, де класичні підходи демонструють низьку чутливість.

У **навчальному процесі** — методичні матеріали для дисциплін, що поєднують графове моделювання даних з кібербезпекою, для спеціальностей 122 «Комп'ютерні науки» та 125 «Кібербезпека та захист інформації» на рівнях бакалаврського та магістерського підготування.

### 7.3. Напрями подальших досліджень

Виконане дослідження відкриває низку перспективних напрямів.

**Розширення експериментальної бази.** Перевірка методу на додаткових датасетах — CSE-CIC-IDS2018 (розширена версія CICIDS зі схожою методологією), UNSW-NB15 (незалежна лабораторія, інші типи атак), CTU-13 (botnet-орієнтований датасет). Виявлення меж узагальнення методу є важливим кроком перед промисловим впровадженням.

**Інтеграція з ML-розширеним baseline.** Порівняння запропонованого графового методу з flow-centric baseline на основі Random Forest / XGBoost / LightGBM класифікаторів дасть ширшу картину його ефективності відносно state-of-the-art flow-centric рішень, за межами простого rule-based підходу.

**Експериментальне порівняння з GNN-методами.** Прямі порівняння з представниками класу temporal graph neural networks (Euler [6], CyberGFM та ін.) на однакових датасетах та обчислювальних ресурсах дозволять кількісно оцінити trade-off «інтерпретовність проти точності» між класичними та нейромережевими графовими підходами.

**Адаптивні параметри.** Поточна реалізація використовує статично налаштовані ваги $w_1, w_2, w_3$ та поріг $\theta_A$. Адаптація цих параметрів у runtime — через online learning з feedback-петлею від оператора SOC, що позначає підтверджені інциденти — підвищить ефективність методу у нестаціонарних мережах.

**Потоковий режим обробки.** Розширення методу на real-time обробку через інтеграцію з streaming-платформами (Apache Kafka → Neo4j Streams, Apache Flink → Neo4j Sink) дозволить перейти від batch-сценарію до production-grade IDS з sub-second latency.

**Інтеграція з threat intelligence.** Збагачення графової моделі даними з TI-джерел (MITRE ATT&CK, відкриті IoC-бази) через додаткові типи вузлів та ребер може суттєво підвищити інтерпретовність результатів: графові патерни детекції стануть прив'язаними до конкретних tactic/technique з kill chain.

**Адаптація для спеціалізованих мереж.** Перенесення методу на специфічні класи мереж — IoT, SCADA, тактичні військові mesh-мережі — з їх характерними топологічними особливостями та attack-моделями відкриває окремий напрям дослідження.

**Роздільна оцінка attacker- і victim-каналів.** Діагностичний аналіз результатів (розділ 6.6, Обмеження 7) виявив, що значна частка помилкових спрацьовувань та пропусків у поточному host-window протоколі концентрується на **victim-хостах** — серверах, що приймають atk-трафік і структурно виглядають як легітимні high-fanout receivers. Пропонується декомпозиція композитної метрики на два канали зі специфічними сигналами:

- $A_{\mathrm{src}}(v, t)$ — композит, обчислений лише на out-ребрах з $v$ (betweenness, community change, Jaccard drift — усі на source-проекції підграфа);
- $A_{\mathrm{dst}}(v, t)$ — композит на in-ребрах до $v$ (включно з додатковими flow-centric сигналами — sharp inbound rate change, SYN/ACK ratio shift).

Рішення про аномалію приймається роздільно: $D_{\mathrm{attacker}}(v, t) = 1$, якщо $A_{\mathrm{src}}(v, t) > \theta_{\mathrm{src}}$; $D_{\mathrm{victim}}(v, t) = 1$, якщо $A_{\mathrm{dst}}(v, t) > \theta_{\mathrm{dst}}$. Такий підхід має три очікувані переваги: (1) вища precision за рахунок розвантаження graph-channel від victim-класу, (2) різна SOC-інтерпретація — attacker-alert потребує containment, victim-alert — hardening, (3) можливість feature-level fusion, де graph-сигнали уточнюють flow-centric рішення. Реалізація вимагає модифікації GDS-проекцій для directed subgraph processing (параметр `relationshipOrientation: 'NATURAL' | 'REVERSE'` у `gds.graph.project`), що технічно просто на Neo4j 2026.x.

Сукупність перелічених напрямів утворює програму досліджень, що може розвиватися у форматі серії публікацій та становить основу для подальшої дисертаційної роботи.
